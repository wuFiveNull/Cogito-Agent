### 2.3 模块组装方式

Cogito-Agent 的模块组装通过 **Composition Root** 完成，位于 `application/runtime_factory.py` 的 `build_runtime_kernel()` 函数。

**组装流程**：

```python
# 简化后的 build_runtime_kernel()
def build_runtime_kernel(db, *, budget, model_adapter, capability_registry, ...):
    # Step 1: 创建基础设施
    policy = policy_engine or PolicyEngine()

    # Step 2: 使用 Database 工厂创建运行时服务（适配器实例）
    services = db.create_runtime_services(
        capability_registry=capability_registry,
        policy_engine=policy,
    )

    # Step 3: 装配记忆服务（如果能力注册表可用）
    if capability_registry is not None:
        retrieval_service = create_retrieval_service(db)
        memory_svc = MemoryApplicationService(db, retrieval_service=retrieval_service)
        memory_svc.register_with_capability_registry(capability_registry)

        # Memorizer + Consolidation（需要模型适配器）
        if model_adapter:
            memorizer = Memorizer(db)
            consolidation_svc = ConsolidationService(memorizer, ...)

    # Step 4: 创建内核（注入所有端口）
    kernel = RuntimeKernel(services, budget=budget, model_adapter=model_adapter, ...)

    # Step 5: 设置可选服务
    kernel.set_memory_service(memory_svc)
    kernel.set_consolidation_service(consolidation_svc)

    return kernel
```

### 2.4 关键耦合机制

**机制一：Ports/Adapters（端口适配器模式）**

`runtime/ports.py` 定义了 7 个核心 Protocol 接口：

```python
class RuntimePersistencePort(Protocol): ...   # 持久化
class RuntimeTracePort(Protocol): ...         # 追踪
class RuntimeAuditPort(Protocol): ...         # 审计
class RuntimeCapabilityExecutorPort(Protocol): ...  # 能力执行
class RuntimePolicyPort(Protocol): ...         # 策略评估
class RuntimeCapabilityCatalogPort(Protocol): ...   # 能力目录
class RuntimeArtifactWriterPort(Protocol): ...       # 工件写入
```

`RuntimeKernel` **只依赖这些 Protocol，不依赖任何具体实现**。具体实现在 `storage/runtime_persistence.py`、`trace/tracer.py`、`governance/policy.py` 中。

**机制二：`RuntimeServices` 数据类打包**

```python
@dataclass(frozen=True)
class RuntimeServices:
    persistence: RuntimePersistencePort
    tracer: RuntimeTracePort
    audit: RuntimeAuditPort
    policy: RuntimePolicyPort
    capability_catalog: RuntimeCapabilityCatalogPort | None = None
    capability_executor: RuntimeCapabilityExecutorPort | None = None
```

所有端口通过一个不可变数据类注入内核。

**机制三：`Database.create_runtime_services()` 工厂方法**

`Database` 负责创建所有适配器实例并装配为 `RuntimeServices`：

```python
# storage/database.py
class Database:
    def create_runtime_services(self, capability_registry, policy_engine, artifact_writer) -> RuntimeServices:
        tracer = TraceStore(self)
        audit = AuditStore(self)
        persistence = RuntimePersistence(self)
        executor = GovernedCapabilityExecutor(policy_engine, ...)
        return RuntimeServices(
            persistence=persistence, tracer=tracer, audit=audit,
            policy=policy_engine, capability_executor=executor, ...
        )
```

**机制四：严格的依赖规则（CLAUDE.md 中明确定义）**

```
- runtime 不得 import 具体模型提供者、工具实现、存储驱动或 UI 通道
- capability 不得绕过 governance（策略/审批）
- memory 不得直接调用模型
- api 不得直接写入存储（只能通过应用服务）
```

### 3.3 关键耦合机制

**机制一：双总线架构（核心精华）**

```
MessageBus (异步队列)                        EventBus (类型化发布-订阅)
────────────────────                        ────────────────────────
通道 ↔ Agent 通信                            系统内部生命周期 hook
asyncio.Queue (点对点)                       Gate (可改写) + Tap (只读观察)
publish_inbound / consume_inbound            emit / observe / fanout / enqueue
publish_outbound / dispatch_outbound         按事件类型注册 handler
```

为什么用两个总线？
- MessageBus 是 **基础设施**（通道和核心之间的管道）
- EventBus 是 **领域逻辑**（核心内部的扩展机制）
- 通道不需要知道 EventBus 的存在
- 生命周期 hook 不经过异步队列，性能更好

**机制二：Phase Slot 系统**

```python
class PluginMemoryModule:
    slot = "before_turn.plugin_memory"       # 唯一标识
    requires = ("before_turn.retrieval",)     # 声明依赖
    produces = ("memory_block",)              # 声明产出

    async def run(self, frame: BeforeTurnFrame) -> BeforeTurnFrame:
        ctx = frame.output
        ctx.retrieved_memory_block += "\n增强记忆"
        return frame
```

Phase 框架自动进行拓扑排序，模块之间通过 Frame 传递数据，不直接共享状态。

**机制三：Gate vs Tap 读写分离**

- **Gate**（`emit`）：插件可改写 Context，支持 abort 提前结束
- **Tap**（`observe`/`fanout`）：插件只观察、做副作用，不可改写

**机制四：ToolsetProvider 可插拔协议**

```python
class ToolsetProvider(Protocol):
    def register(self, registry: ToolRegistry, deps: ToolsetDeps) -> ToolsetRegistrationResult: ...
```

每个 Provider 负责注册一组相关工具，由 `config.toml` 的 `wiring.toolsets` 配置启用。

**机制五：Plugin 与核心的隔离**

插件只依赖 `EventBus` 和 `PluginContext`，不依赖任何 Agent 内部类。插件拥有 **9 个扩展点**：6 个 EventBus hook + Tool 注册 + ToolHook + Channel。

### 4.3 关键耦合机制

**机制一："窄腰"设计哲学**

```
核心（窄腰） → Provider 适配器 / 工具 / MCP / 技能 → 边缘
```

核心原则：
- **每个核心工具都发送到每次 API 调用**，所以新增核心工具的阈值极高
- 新能力优先级：扩展现有代码 → CLI 命令+技能 → 服务门控工具 → 插件 → MCP → 新核心工具

**机制二：Footprint Ladder（能力决策阶梯）**

```
1. 扩展现有代码 — 零新增表面积
2. CLI 命令 + 技能 — 零模型工具表面积
3. 服务门控工具 (check_fn) — 仅在条件满足时出现
4. 插件 — 第三方/用户特定能力，不进入核心
5. MCP 服务器 — 通过 MCP 协议接入
6. 新核心工具 — 仅当能力是基础性、广泛有用、无法通过终端+文件实现
```

**机制三：Provider Strategy 模式**

每个 LLM API 通过独立的 Adapter 适配：

| Strategy | 适配对象 |
|----------|----------|
| AnthropicAdapter | Claude API |
| BedrockAdapter | AWS Bedrock |
| GeminiNativeAdapter | Google Gemini |
| OpenAIAdapter | OpenAI 兼容 API |
| CodexResponsesAdapter | GitHub Codex |
| ...15+ 更多 | ... |

**机制四：服务门控工具（check_fn）**

```python
# 工具只有在前置条件满足时才会注册到模型
{
    "name": "home_assistant_light",
    "check_fn": lambda ctx: ctx.config.get("ha_token") is not None
}
```

## 6. 模块组装方式对比

### 6.1 三个项目的核心差异

| 维度 | Cogito-Agent | Akashic-Agent | Hermes-Agent |
|------|-------------|---------------|--------------|
| **组装模式** | 工厂函数（纯函数） | 组装类 + 纯函数 | 构造函数注入 |

## 7. 耦合处理机制对比

### 7.1 核心解耦策略总览

| 策略 | Cogito-Agent | Akashic-Agent | Hermes-Agent |
|------|-------------|---------------|--------------|
| **Port/Protocol 接口** | ✅ 7 个核心 Protocol | ✅ 5+ 个 Protocol | ❌ 隐式内部约定 |
| **依赖倒置** | ✅ `runtime` 不依赖具体实现 | ✅ Channel 不依赖 Agent | ✅ Provider Adapter |
| **事件驱动** | ❌ 无 EventBus | ✅ 双总线 | ✅ Conversation Loop |
| **插件系统** | ❌ 无 | ✅ 9 扩展点 | ✅ Footprint Ladder |
| **策略模式** | ✅ Provider Adapter | ✅ Provider Strategy | ✅ 15+ Provider 适配器 |
| **门控模式 (Gate)** | ❌ 无 | ✅ emit/observe 分离 | ❌ check_fn 工具门控 |
| **配置驱动** | ❌ 代码组装 | ✅ wiring 配置 | ✅ config.yaml |
| **依赖规则文件化** | ✅ CLAUDE.md 明确定义 | ✅ ARCHITECTURE.md | ✅ AGENTS.md |

### 7.2 Cogito-Agent 的解耦细节

**严格的六边形架构**：

```
                    ┌─────────────┐
                    │   外部世界   │
                    │ (CLI/Web)   │
                    └──────┬──────┘
                           │
               ┌───────────▼───────────┐
               │   Application Layer    │  ← 渠道无关的应用服务
               │   (Chat/Session/Mem)  │
               └───────────┬───────────┘
                           │
               ┌───────────▼───────────┐
               │   RuntimeKernel       │  ← 只依赖 Ports (Protocols)
               │   (编排，不依赖实现)    │
               └───────────┬───────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ Persistence  │  │   Tracer     │  │   Policy     │
│ (SQLite)     │  │ (TraceStore) │  │ (PolicyEng)  │
└──────────────┘  └──────────────┘  └──────────────┘
```

**禁止的依赖（在 CLAUDE.md 中明确定义）**：
```
运行时层 (runtime)
  → 不得 import 具体模型提供者
  → 不得 import 具体工具实现
  → 不得 import 存储驱动
  → 不得 import UI 通道

能力层 (capability)
  → 不得绕过治理层 (governance)

记忆层 (memory)
  → 不得直接调用模型

API 层 (api)
  → 不得直接写入存储（只能通过应用服务）
```

### 7.3 Akashic-Agent 的解耦细节

**双总线的解耦价值**：

```
                       MessageBus (异步队列)
  ┌──────────┐  publish_inbound   ┌──────────┐
  │ Telegram │ ──────────────────►│ AgentLoop │
  │ Channel  │                    │ (消费者)  │
  └──────────┘                    └────┬─────┘
                                       │ EventBus (同步)
  ┌──────────┐  publish_outbound  ┌────▼─────┐
  │   QQ     │ ◄──────────────────│ Lifecycle │
  │ Channel  │                    │  Phase    │
  └──────────┘                    └──────────┘
```

**MessageBus 的特点**：
- Channel 不知道 Agent 的存在——只往 Queue 投消息
- Agent 不知道 Channel 的存在——只从 Queue 消费消息
- 天然支持异步、重试、降级

**EventBus 的特点**：
- Gate 模式（emit）：插件可改写上下文，支持 abort
- Tap 模式（observe/fanout/enqueue）：插件只观察，不可改写
- 类型安全的事件分派

**Phase 模块的 Slot 解耦**：

```python
# 每个模块声明 requires/produces，不依赖其他模块的具体实现
class BeforeTurnModule:
    slot = "before_turn.retrieval"
    requires = ()
    produces = ("history", "memory_blocks", "skill_mentions")
    # 其他模块依赖 produces 的输出
```

拓扑排序自动决定执行顺序，没有硬编码的阶段依赖。

### 7.4 Hermes-Agent 的解耦细节

**"窄腰"哲学**：

```
           ┌──────────┐
           │  Chats   │  ← Telegram、Discord、Slack、CLI...
           └────┬─────┘
                │
         ┌──────▼──────┐
         │ Conversation │  ← 核心循环（窄腰）
         │    Loop      │
         └──────┬──────┘
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
  ┌──────┐ ┌──────┐ ┌──────┐
  │Anthrop│ │Gemini│ │Bedroc│  ← Provider 适配器
  └──────┘ └──────┘ └──────┘
```

**Footprint Ladder** 是 Hermes 的核心解耦策略——它不是通过架构机制，而是通过**决策过程**来控制耦合：

1. 扩展现有代码（零新增表面积）
2. CLI 命令 + 技能（零模型工具表面积）
3. 服务门控工具（条件注册）
4. 插件（用户空间扩展）
5. MCP 服务器（协议级集成）
6. 新核心工具（最终手段）

**服务门控**（check_fn）是一种轻量级解耦：

```python
# 工具只在条件满足时暴露给模型
tools = [
    {"name": "web_search", "check_fn": lambda ctx: ctx.has_web_access},
    {"name": "home_assistant", "check_fn": lambda ctx: ctx.config.get("ha_token")},
]
```

### 7.5 耦合度对比

| 耦合维度 | Cogito-Agent | Akashic-Agent | Hermes-Agent |
|---------|-------------|---------------|--------------|
| **内核耦合度** | 低（纯 Protocol 依赖） | 低（双总线 + EventBus） | 中（大型对象内部耦合） |
| **渠道耦合度** | 低（应用服务层隔离） | 极低（MessageBus 隔离） | 中（直接调用核心） |
| **Provider 耦合度** | 低（Protocol + 策略模式） | 低（Strategy 模式） | 低（Strategy 模式） |
| **工具耦合度** | 中（通过 Capability Registry） | 低（ToolRegistry + ToolsetProvider） | 中（静态工具定义） |
| **存储耦合度** | 低（Port + Adapter） | 中（文件系统） | 中（多种后端） |
| **模块间依赖** | 显式（Protocol） | 显式（Protocol + Frame） | 隐式（内部调用） |
| **测试可mock性** | 高（Protocol 可轻松 Mock） | 高（EventBus 可 Mock） | 中（需 Mock 大型对象） |

## 8. 总结与启示

### 8.1 三个项目的共同设计模式

1. **组合根（Composition Root）** — 三个项目都坚持唯一组装点，没有 Service Locator 或全局自动注入
2. **Python Protocol 作为 SPI 边界** — Cogito 和 Akashic 广泛使用，Hermes 也有类似约定
3. **Provider 策略模式** — 所有项目都通过 Strategy 模式隔离 LLM API 差异
4. **无 IoC 容器** — 全手动依赖注入，无 Spring-like 隐式扫描
5. **本地优先** — 所有项目都设计为可在本地完整运行

### 8.2 三个项目的独特亮点

| 亮点 | 属于 | 描述 |
|------|------|------|
| **严格的依赖规则** | Cogito-Agent | 在 CLAUDE.md 中用文字精确描述禁止的依赖方向 |
| **双总线架构** | Akashic-Agent | MessageBus（通道通信）+ EventBus（生命周期 hook），职责严格分离 |
| **Phase Slot 系统** | Akashic-Agent | 插件模块通过 requires/produces 声明式表达依赖，自动拓扑排序 |
| **Footprint Ladder** | Hermes-Agent | 用决策过程控制耦合——不是依赖机制，而是团队纪律 |
| **RuntimeServices 打包** | Cogito-Agent | 所有端口以不可变 DataClass 注入，接口契约清晰 |
| **9 个插件扩展点** | Akashic-Agent | 插件可以在生命周期的所有阶段介入 |
| **服务门控工具** | Hermes-Agent | 轻量级的条件工具注册，无需复杂的权限系统 |

### 8.3 架构启示

**对于模块划分**：
- Cogito-Agent 的 22 个模块提供了最清晰的边界定义，适合需要长期演进的系统
- Akashic-Agent 的 16 个模块聚焦在核心域的纯净性，适合需要高度插件化的框架
- Hermes-Agent 的巨文件+适配器模式适合快速扩展多平台支持的场景

**对于耦合处理**：
- 如果从零开始构建，建议采用 **Cogito-Agent 的 Ports/Adapters + Akashic 的双总线**——既有清晰的接口边界，又有灵活的事件驱动机制
- Ports/Adapters 适合核心编排层的解耦，EventBus 适合业务扩展点的解耦
- "窄腰"设计哲学适合控制核心膨胀，Footprint Ladder 适合团队做技术决策

**对于组装方式**：
- 工厂函数（Cogito）比构造函数注入（Hermes）更易于测试和组合
- 生命周期管理（Akashic 的 AppRuntime.start/shutdown）对于有后台任务的服务模式必不可少
- Setter 注入适合可选服务，构造函数注入适合必需依赖
