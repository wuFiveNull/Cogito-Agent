## 1. QwenPaw — 轻量级上下文管理

### 1.1 概述

QwenPaw 是一个基于 **AgentScope** 框架构建的多智能体系统。其上下文管理采用经典的 **InMemoryMemory + LLM 摘要压缩** 模式，在 `agents/context/` 目录下实现了一套轻量但完整的上下文生命周期管理。

### 1.2 上下文分段

QwenPaw 的最终模型输入（由 `LightContextManager` 的 `pre_reasoning` 和 `pre_reply` 钩子组装）由以下几部分组成：

| 段位 | 内容 | 来源 |
|------|------|------|
| **系统提示词 (System Prompt)** | `agent.sys_prompt` — 从配置文件加载的代理身份与行为规则 | `ReActAgent.sys_prompt` |
| **压缩摘要 (Compressed Summary)** | 之前轮次经过 LLM 压缩的结构化摘要 | `AgentContext._compressed_summary` |
| **活跃消息 (Active Messages)** | 本轮保留在内存中的最近 N 条消息（role=user/assistant/tool） | `AgentContext.content`（过滤掉标记为 COMPRESSED 的消息） |
| **检索记忆 (Retrieved Memory)** | `pre_reply` 钩子从 `memory_manager.retrieve()` 获取的语义搜索结果 | 外部记忆系统 |
| **当前用户消息** | 用户的当前输入，附有时间戳 | `current_message` |

消息的最终组装顺序（由 AgentScope 的 `ReActAgent` 控制）：

```
System Prompt
Compressed Summary (如果有)
Retrieved Memory (如果有)
保留的活跃消息 (按时间顺序)
当前用户消息
```

### 1.3 压缩机制

QwenPaw 的压缩在 `LightContextManager.pre_reasoning()` 中触发，在每次推理步骤前检查上下文大小。

#### 1.3.1 触发条件

```
计算阈值:
  context_compact_threshold = max_input_length × compact_threshold_ratio  (默认 ~80%)
  context_compact_reserve   = max_input_length × reserve_threshold_ratio  (默认 ~10%)

检查:
  sys_tokens + summary_tokens + messages_tokens > context_compact_threshold
```

#### 1.3.2 消息切分

由 `AsMsgHandler.context_check()` 实现：

1. 计算全部消息的总 token 数
2. 如果未超阈值（`total < threshold`），不压缩
3. 如超阈值，从尾部往前扫描，找到满足以下条件的最多保留数：
   - 保留消息的 token 总数 ≤ `context_compact_reserve`
   - tool_use_id 与 tool_result_id 配对完整（不允许截断工具调用链）
4. 返回 `(要压缩的旧消息, 保留的新消息, total_tokens, keep_tokens)`

#### 1.3.3 LLM 摘要压缩

由 `_compact_context()` 实现：

1. 将要压缩的旧消息格式化为结构化文本（`AsMsgHandler.format_msgs_to_str()`）
2. 使用 LLM（通过 `ReActAgent`）生成结构化的压缩摘要，格式如下：

```
## Goal
[用户要完成什么]

## Constraints & Preferences
[约束和偏好]

## Progress
### Done
### In Progress
### Blocked

## Key Decisions

## Next Steps

## Critical Context
```

3. **增量更新**：如果已有 `previous_summary`，LLM 会收到新旧两部分，要求保留旧信息、补充新进展
4. **校验**：检查摘要是否包含 `##` 标题标记（`_is_valid_summary()`）
5. **失败降级**：如果 LLM 摘要失败或格式无效，采用"保守保留策略"——将保留阈值放大到 `left_compact_threshold`，保留更多消息，丢弃更旧的

#### 1.3.4 工具结果裁剪

由 `post_acting` 钩子在每次工具调用后触发：

1. 近期的 N 条工具结果使用较大的字节限制（`recent_max_bytes`）
2. 较旧的工具结果使用较小的字节限制（`old_max_bytes`，默认 3000 字节）
3. 超出限制的 tool_result 被截断，完整内容写入缓存文件
4. 豁免列表（特定文件扩展名或工具名称）不受旧结果截断影响

#### 1.3.5 历史持久化

压缩后，被压缩的消息通过 `mark_messages_compressed()` 持久化到 `dialog/YYYY-MM-DD.jsonl` 文件中，然后从内存中移除。

#### 1.3.6 关键配置参数

| 参数 | 说明 |
|------|------|
| `compact_threshold_ratio` | 压缩触发阈值与 max_input_length 的比例（默认 ~0.8） |
| `reserve_threshold_ratio` | 压缩后保留消息的 token 比例（默认 ~0.1） |
| `compact_with_thinking_block` | 是否在传给压缩 LLM 的消息中包含 thinking 块 |
| `pruning_old_msg_max_bytes` | 旧工具结果截断字节数 |
| `pruning_recent_msg_max_bytes` | 新工具结果截断字节数 |
| `offload_retention_days` | 缓存文件的保留天数 |

## 2. akashic-agent — 模块化 Prompt Block 系统

### 2.1 概述

akashic-agent 采用了高度模块化的 **SystemPromptBuilder + PromptBlock** 架构，将系统提示词拆分为多个独立的"积木块"（Prompt Block），每个块有优先级、缓存签名和独立渲染逻辑，最终由 `PromptAssembler` 统一组装。

### 2.2 上下文分段

akashic-agent 的上下文最终输出由 `ContextBuilder.render()` → `PromptAssembler.assemble()` 生成，分为两大区域：

#### 2.2.1 System Prompt 区（稳定的系统级指令）

由 8 个 `PromptBlock` 按优先级升序拼接，以 `\n\n---\n\n` 分隔：

| 优先级 | Block 名称 | 内容 | 稳定性 |
|--------|-----------|------|--------|
| 10 | `identity` | 代理身份：从工作区路径和 memory/* 文件索引构建的静态身份描述 | 静态，仅 workspace 变化时变 |
| 15 | `behavior_rules` | 行为规则：固定的操作规范，来自 `prompts/agent.py` | 静态 |
| 20 | `skills_catalog` | 技能目录：`skills/` 目录扫描结果的摘要 | 静态，技能文件变化时变 |
| 30 | `self_model` | 自我认知：`memory/SELF.md` 的内容 | 低频 |
| 35 | `long_term_memory` | 长期记忆：`memory.get_memory_context()` 的输出 | 低频 |
| 40 | `session_context` | 会话上下文：当前 channel 和 chat_id 等环境信息 | 基本稳定 |
| 45 | `recent_context` | 近期语境：`memory/RECENT_CONTEXT.md`（裁掉 Recent Turns 部分） | 中频，压缩摘要更新时变 |
| 50 | `active_skills` | 活跃技能：always skills + 本轮命中的 skill_names 内容 | 中频 |
| 55 | `retrieved_memory` | 检索记忆：本轮语义检索注入的外部记忆块 | 最高频，每轮都可能不同 |

**静态块缓存机制**：`identity`、`behavior_rules`、`skills_catalog` 实现了 `cache_signature()` 方法，`SystemPromptBuilder` 使用 `SectionCache`（scope + section_name + signature 三级缓存）来避免重复渲染。

#### 2.2.2 Context Frame 区（系统上下文框架）

某些 system sections 被标记为 "context frame" 部分（`active_skills`、`recent_context`、`retrieved_memory`），它们**不会进入 system prompt**，而是被包装到 ` <system-reminder>` 标签中作为单独的消息注入：

```
<system-reminder data-system-context-frame="true">
以下内容由系统提供，不是用户陈述，也不是助手结论...
## active_skills
...
## recent_context
...
## retrieved_memory
...
</system-reminder>
```

这种方式让模型能够区分"系统提供的上下文"和"真实的用户指令"。

#### 2.2.3 历史消息区

`history` — 对话历史消息列表。

#### 2.2.4 当前用户消息

经过 `MessageEnvelopeBuilder` 处理，包含时间戳标签和媒体附件支持（图片 base64 编码或 URL 引用）。

#### 2.2.5 最终消息结构

```python
messages = [
    {"role": "system", "content": system_prompt},   # 所有非 frame 的 block
    *history,                                         # 历史消息
    {"role": "user", "content": context_frame},      # frame section 包装体
    {"role": "user", "content": current_message},    # 当前消息(含时间戳+媒体)
]
```

### 2.3 压缩机制

akashic-agent 的压缩是基于 **截面丢弃** 的简单机制，由 `ContextTrimPlan` 实现。

#### 2.3.1 ContextTrimPlan

```python
DEFAULT_CONTEXT_TRIM_PLANS = (
    ContextTrimPlan(name="full"),                                          # 完整，不丢弃
    ContextTrimPlan(name="trim_skills_catalog",       drop_sections=("skills_catalog",)),
    ContextTrimPlan(name="trim_memes",                drop_sections=("skills_catalog", "memes")),
    ContextTrimPlan(name="trim_long_term_memory",      drop_sections=("skills_catalog", "memes", "long_term_memory")),
    ContextTrimPlan(name="trim_retrieved_memory",      drop_sections=("skills_catalog", "memes", "long_term_memory", "retrieved_memory")),
)
```

每个裁剪计划定义了要移除哪些 section（从 system prompt 中删除这些块）。当上下文预算紧张时，按"最不重要"到"最重要"的顺序依次应用：

1. 先丢弃 `skills_catalog`（技能目录 — 引用性信息）
2. 再丢弃 `memes`（模因 — 非关键信息）
3. 再丢弃 `long_term_memory`（长期记忆 — 可以重新检索）
4. 最后丢弃 `retrieved_memory`（检索记忆 — 最接近当前对话但仍然可以放弃）

#### 2.3.2 压缩触发

由 `looping/core.py` 中的预算检查逻辑驱动，在 `agent/prompting/budget.py` 中定义裁剪计划常量。当估计 token 量超过上下文限制时，按照裁剪计划依次丢弃非关键 section。

#### 2.3.3 特点

- **无 LLM 调用**：压缩完全不依赖 LLM 生成摘要，纯由 system prompt section 的增删实现
- **可逆性弱**：删除的 section 在后续轮次中不可恢复（除非通过技能重新加载或记忆重新检索）
- **适用于"无限上下文"模型**：对于支持长上下文的模型（如 Gemini 1M+），减少 system prompt 大小比压缩历史更关键

## 3. hermes-agent — 工业级上下文压缩引擎

### 3.1 概述

hermes-agent 拥有三个项目中最复杂的上下文管理系统。其核心是 `ContextCompressor`（实现 `ContextEngine` 接口），采用 **四阶段压缩流水线**，并结合了会话分裂（session rotation）、辅助模型摘要、防抖动、预算校准等工业级特性。系统提示词构建由 `system_prompt.py` 配合 `CodingContextProfile` 驱动。

### 3.2 上下文分段

hermes-agent 的上下文最终发送给 LLM 的消息结构：

#### 3.2.1 System Prompt

由多个构建阶段组成：

| 阶段 | 内容 | 说明 |
|------|------|------|
| **核心系统提示词** | 从配置加载的基础身份和行为说明 | 每个会话构建一次 |
| **编码上下文块** (Coding Blocks) | `coding_context.py` 中的 `CODING_AGENT_GUIDANCE` + 工作区快照 | 仅在 coding posture 下注入。工作区快照包括：git 分支/状态、最近提交、项目标记文件、包管理器、验证命令 |
| **记忆块** (Memory Block) | 从 MemoryProvider 检索的 MEMORY.md / USER.md 内容 | 由 `memory_manager.build_memory_context_block()` 构建 |
| **规则/技能块** (Rules/Skills) | 用户配置的技能索引和操作规则 | 技能目录的摘要 |

#### 3.2.2 历史消息

完整的 `messages` 列表，包含 user/assistant/tool 三种角色的完整对话历史。系统提示词位于列表第一个元素（role=system）。

#### 3.2.3 @ 上下文引用

由 `context_references.py` 实现，用户可以在消息中使用 `@file:path`、`@folder:path`、`@diff`、`@staged`、`@git`、`@url:...` 等语法引用外部内容，在发送前展开为内联代码块。有软限制（25% context_length）和硬限制（50% context_length）两层保护。

#### 3.2.4 压缩摘要

压缩后，生成的摘要作为一条独立消息插入历史，附有特殊元数据 `_compressed_summary: True` 和清晰的边界标记。

### 3.3 压缩机制

hermes-agent 的压缩由 `ContextCompressor.compress()` 驱动，是三个项目中最精密的实现。

#### 3.3.1 触发条件

**双路径检查**：

1. **预检测** (`should_compress_preflight`)：在 API 调用前，使用 `estimate_request_tokens_rough()` 估算 token 量，若超过 `threshold_tokens` 则触发压缩
2. **真实检测** (`should_compress`)：API 返回后，使用 `update_from_response()` 记录的 `last_prompt_tokens` 与 `threshold_tokens` 比较

**阈值计算**：

```python
threshold_tokens = max(context_length × threshold_percent, MINIMUM_CONTEXT_LENGTH)
```

对于小上下文窗口（≤ MINIMUM_CONTEXT_LENGTH），使用 85% 的窗口大小作为阈值，确保压缩能在 provider 拒绝请求前触发。

**防抖动**：如果最近 2 次压缩的节省率 < 10%，自动跳过压缩以避免无效循环。

#### 3.3.2 压缩流水线（四阶段）

**Phase 1: 工具结果裁剪** (`_prune_old_tool_results`)

三道子工序：

| 子工序 | 方法 | 说明 |
|--------|------|------|
| Pass 1: 去重 | MD5 hash 对比 | 相同文件被多次读取时，只保留最新的完整副本，旧副本替换为 `[Duplicate tool output — same content as a more recent call]` |
| Pass 2: 替换为摘要 | `_summarize_tool_result()` | 每个旧工具结果替换为 1 行摘要，如 `[terminal] ran 'npm test' -> exit 0, 47 lines output` |
| Pass 3: 截断参数 | `_truncate_tool_call_args_json()` | 超过 500 字符的工具调用参数字符串在 JSON 结构内截断（保持 JSON 合法性） |

裁剪边界由 token 预算驱动（`protect_tail_tokens`），而不是固定消息条数。

**Phase 2: 确定边界**

```
compress_start = protect_head_size(messages)          # 保护头部 N 条
compress_start = align_boundary_forward(messages, ...) # 向前对齐到完整消息边界
compress_end = find_tail_cut_by_tokens(messages, ...)  # 尾部由 token 预算决定
```

- 头部保护：`protect_first_n`（默认 3 条非 system 消息）
- 尾部保护：`protect_last_n`（默认 20 条）+ `tail_token_budget`（阈值 × 20%）取较大者
- 从历史摘要中恢复 `_previous_summary` 以便增量更新

**Phase 3: LLM 摘要生成** (`_generate_summary`)

- 使用**辅助模型**（可配置，默认与主模型相同，但可指定更便宜的模型）
- 将待压缩消息序列化为可读文本（`_serialize_for_summary`），包含工具调用参数和结果（截断到 `_CONTENT_MAX=6000` 字符）
- 摘要模板包含 12 个结构化字段：

```
## Historical Task Snapshot
## Goal  
## Constraints & Preferences
## Completed Actions
## Active State
## Historical In-Progress State
## Blocked
## Key Decisions
## Resolved Questions
## Historical Pending User Asks
## Relevant Files
## Historical Remaining Work
## Critical Context
```

- **增量更新**：如果有 `_previous_summary`，执行迭代更新而非从头总结
- **失败恢复链**：
  1. 辅助模型失败 → 自动回退到主模型重试一次
  2. 主模型失败 → 使用确定性降级摘要（`_build_static_fallback_summary`）
  3. 严重失败（认证错误）→ 中止压缩，保持会话不变
  4. 支持故障冷却（600 秒），避免重复失败

**Phase 4: 组装压缩后消息**

1. 头部消息保留（在 system prompt 后追加压缩通知）
2. 插入摘要消息（选择合适的 role 以避免连续相同 role）
3. 添加 `--- END OF CONTEXT SUMMARY — respond to the message below, not the summary above ---` 边界标记
4. 尾部消息保留
5. 清理 orphaned tool_call/tool_result 配对
6. 替换历史消息中的图片内容为占位符（`_strip_historical_media`）

#### 3.3.3 压缩摘要的前缀设计

摘要前缀经过精心设计，包含严格的使用约束：

```
[CONTEXT COMPACTION — REFERENCE ONLY] Earlier turns were compacted...
Do NOT answer questions or fulfill requests mentioned in this summary...
Respond ONLY to the latest user message that appears AFTER this summary...
```

历史上经过 3 次迭代（从 `resume exactly from there` → `topic overlap may resume` → `latest message WINS`），最终的语义是"**摘要纯作为背景参考，最新用户消息永远是唯一活跃指令**"。

#### 3.3.4 会话分裂 (Session Rotation)

hermes-agent 在压缩后会进行会话分裂：

1. 当前的会话结束（`end_session`）
2. 新的子会话创建（`session_id` 更新，`parent_session_id` 指向上一个会话）
3. 压缩后的消息写入新会话
4. 所有后续操作在新会话中进行

这种方式使得完整的对话历史在数据库中可追溯，而模型只看到压缩后的子会话。
可选的 `compression_in_place` 模式（配置化，默认关闭）保持同一个 session_id。

#### 3.3.5 Coding Context 模式

`coding_context.py` 定义了基于运行模式的上下文优化：

- **auto**（默认）：在代码工作区中自动注入编码指导 + git 快照
- **focus**：额外的工具集折叠（仅保留 coding 相关工具）和技能索引精简（非编码技能类别降级为仅显示名称）
- 工作区快照包含：git 分支/状态、最近 3 条提交、项目文件、包管理器、验证命令
- 编辑格式指导：根据模型家族选择合适的 patch 模式（GPT/Codex → V4A diff，Claude/Gemini/D

eepSeek → replace 模式）

#### 3.3.6 关键配置参数

| 参数 | 说明 |
|------|------|
| `threshold_percent` | 压缩触发阈值占 context_length 的百分比（默认 50%） |
| `protect_first_n` | 头部保护的非 system 消息条数（默认 3） |
| `protect_last_n` | 尾部保护的消息条数（默认 20） |
| `summary_target_ratio` | 摘要 token 预算占阈值的比例（默认 20%） |
| `summary_model_override` | 辅助压缩模型的名称 |
| `abort_on_summary_failure` | 摘要失败时是否完全中止压缩（默认 False） |
| `compression_in_place` | 是否原地压缩（不旋转 session_id，默认 False） |
| `quiet_mode` | 静默模式（不输出日志） |

## 4. 横向对比总结

### 4.1 上下文分段对比

| 分段 | QwenPaw | akashic-agent | hermes-agent |
|------|---------|---------------|--------------|
| **身份/规则** | system_prompt（整体加载） | identity + behavior_rules 两个 block | 核心 system prompt（整体构建）+ 编码上下文块 |
| **技能/能力** | 无独立分段 | skills_catalog + active_skills 两个 block | skill index（可被编码模式精简） |
| **自我认知** | 无 | SELF.md 独立 block | MEMORY.md / USER.md（记忆块） |
| **长期记忆** | 外部 memory_manager | long_term_memory block | memory block |
| **近期语境** | 无独立分段 | recent_context block（从 RECENT_CONTEXT.md） | 无独立分段，由 token-budget 尾部保护实现 |
| **检索记忆** | prepend_summary 嵌入 | retrieved_memory block（context frame 内） | 记忆块的一部分 |
| **历史消息** | 内存中全部活跃消息 | history 列表 | 完整 messages 列表 |
| **当前消息** | Msg 对象 | 时间戳包裹 + 可选媒体 | 时间戳包裹 + 可选 @引用展开 + 媒体 |
| **压缩摘要** | 前置为一条"系统用户"消息 | 无（采用丢弃而非摘要） | 作为独立消息插入，带边界标记 |
| **上下文框架** | 无 | `<system-reminder>` 包装 frame sections | 无特殊包装，但摘要前缀含使用约束 |

### 4.2 压缩方式对比

| 维度 | QwenPaw | akashic-agent | hermes-agent |
|------|---------|---------------|--------------|
| **核心策略** | LLM 摘要 + 消息丢弃 | 按优先级丢弃 system prompt section | 工具结果裁剪 + LLM 摘要 + 会话分裂 |
| **压缩时机** | pre_reasoning（每次推理前） | 预算不足时 | API 调用后（真实 token 数）+ 预检测 |
| **消息维度** | 按 token 阈值尾部保留 | 按重要性丢弃 section | 按 token 预算保护头尾 + 压缩中间 |
| **压缩模型** | 主模型（ReActAgent） | 无需模型 | 可配置辅助模型 + 主模型降级 |
| **增量更新** | 支持（previous_summary 合并） | 无 | 支持（_previous_summary + 迭代提示） |
| **失败降级** | 扩大保留阈值 | 无 | 三层：辅助→主→确定性降级 |
| **防抖动** | 无 | 无 | 2 次无效压缩后自动跳过 |
| **工具结果处理** | 简单截断 | 无 | 去重 + 智能摘要 + 参数截断 + 图片剥离 |
| **会话持久化** | 压缩消息写入 dialog/*.jsonl | 未体现 | SQLite 会话分裂（session rotation） |
| **模型家族适配** | 无 | 无 | 编辑格式指导（V4A vs replace） |
| **上下文参考注入** | 无 | 无 | `@file`/`@diff`/`@url` 引用语法 + 安全限制 |

### 4.3 架构风格对比

| 维度 | QwenPaw | akashic-agent | hermes-agent |
|------|---------|---------------|--------------|
| **框架依赖** | AgentScope | 自定义，Protocol 接口 | 无框架，直接调用 OpenAI API |
| **扩展性** | Registry 模式注册 Backend | Protocol + PromptBlock 接口 | ABC + Plugin 系统 |
| **复杂度** | ★★☆☆☆（中等） | ★★☆☆☆（中等） | ★★★★★（非常高） |
| **代码量** | ~1300 行 (context 模块) | ~800 行 (context + prompt_block + assembler) | ~2600 行 (context_compressor 仅压缩部分) |
| **适用场景** | 轻量多智能体系统 | 模块化、可插拔的 agent 系统 | 生产级、长对话、编码助手 |

### 4.4 总结

**QwenPaw** 采用经典的 LLM 摘要压缩，实现简洁易懂，通过 AgentScope 框架集成，适合需要基本上下文管理的多智能体场景。其压缩是在消息级别而非 prompt section 级别操作的。

**akashic-agent** 的创新在于将 system prompt 拆分为独立的 Prompt Block，支持优先级排序、静态缓存和选择性丢弃。压缩策略不是"总结旧消息"，而是"按重要性梯度丢弃 system prompt 中的非关键 section"，适合拥有长上下文窗口模型的场景。

**hermes-agent** 拥有最工业化的上下文管理，从工具结果去重、智能摘要、AI 辅助压缩、delta 更新、失败恢复链到会话分裂，覆盖了几乎所有边缘情况。其压缩不仅是"减少消息数"，更是以 token 预算为核心的精细化资源管理，并围绕编码场景做了大量优化（coding posture、工作区快照、编辑格式指导）。
